# HopChase plugin: notes from case 04 (Solana King bot drain)

Written while tracing case 04 with the `hopchase` plugin (skills `trace-funds`, `address-profile`, `case-report`; scripts in `/Users/albert/Projects/hopchase/scripts/`). Each item says what happened, why it matters and what I would change. The fix work belongs in the hopchase project, not here.

## Bugs

1. **`sol_trace.py` drops every version-1 transaction.** `getTransaction` is called with `maxSupportedTransactionVersion: 0` (`sol_trace.py:43`). The victim's arbitrage bot sends version-1 transactions, so 986 of its 1,000 signatures came back as `?? no tx` and the `history` output had 14 transactions instead of 1,000. The RPC error was swallowed: `common.sol_rpc` returns `None` on any error that is not a 429, so the script cannot tell "not found" from "unsupported version". Fix: request `maxSupportedTransactionVersion: 1` (or the highest the node accepts) and print the RPC error message in `sol_rpc` instead of returning `None` silently. The same `0` is in `tools/solana_util.py` of this repository (case checks); case 04 works around it with a local `tx()`.
2. **Unknown mints are printed as raw integers.** `USD1tt… -7,173,929,438` and `7vfCXT… -4,106,158` in the history output are 7,173.93 USD1 (6 decimals) and 0.041 wrapped ETH (8 decimals). `SOL_MINTS` in `common.py` has four entries. Fix: read `decimals` from `preTokenBalances[].uiTokenAmount` (it is in every response already) and format with it; fall back to the raw integer only when the balance arrays are missing. Add USD1, wrapped ETH, PYUSD, USDS, cbBTC to the label table.
3. **`evm_trace.py` misses internal transactions.** The Ethereum destination received all 251 ETH as internal transfers from Mayan's SwiftDest contract. `evm_trace.py` showed two native transactions and "0 token transfers": the bridge payout was invisible. Fix: also fetch `/api/v2/addresses/{a}/internal-transactions` from Blockscout and list value-bearing internal transfers with the calling contract's name.
4. **Mayan is in the program table but not in the bridge lookups.** `bridges.py` knows Bridgers, Wormhole and deBridge. Mayan has a public explorer API: `https://explorer-api.mayan.finance/v3/swap/trx/<source tx>` returns the order (`destAddress`, `fromAmount`, `toAmount`, `status`, `fulfillTxHash`, `refundTxHash`, `sourceStateAddr`), and `/v3/swaps?trader=<address>&limit=50&offset=N` lists orders (with two traps: `limit=200` returns an empty list, and the trader listing omits cancelled and refunded orders, so query per transaction). Add `bridges.py mayan <SIG|ADDRESS>`.
5. **Relay is not covered either.** `https://api.relay.link/requests/v2?hash=<tx>` and `?user=<address>` return the order with `status`, `failReason` (here `BLOCKED_WALLET`), `recipient`, `inTxs`, `outTxs`. Relay's Solana depository `7uTT8Xi5RWXzy7h9XL244GRgEycDYDhLjr3ZyNdXi8pZ` and the program `99vQwtBwYtrqqD9YSXbdum3KBdxPAVxYTaQ3cfnJSrN2` should be labelled `BRIDGE:Relay`. Add `bridges.py relay <TX|ADDRESS>`.
6. **`recheck.py` cannot read Solana token accounts that are not ATAs of a wallet.** It only takes wallets and token accounts by address; that was enough here, but it crashed earlier in the session when `getTokenAccountsByOwner` returned `None` (an RPC hiccup) because the result is indexed without a check. Guard the `None`.
7. **`address-profile` skill references `${CLAUDE_PLUGIN_ROOT}`**, which is not set when the skill is read outside the plugin loader; `trace-funds` hard-codes the path instead. Pick one.

## Gaps in the method

8. **Freeze status is never checked.** The skill says "freeze window open" but has no command for it. Needed: token account `state` (`frozen` / `initialized`) on every hop (`getAccountInfo` jsonParsed), the mint's `freezeAuthority`, and on Ethereum `isBlacklisted(address)` on USDC (`0xfe575a87`) and `isBlackListed(address)` on USDT (`0xe47d6060`) via `eth_call`. In this case the stablecoins sat unfrozen on the drainer for 22 minutes and 232,875 USDC still sit unfrozen in Mayan escrow. Add a `freeze` subcommand to `sol_trace.py` and `evm_trace.py`, and a line in the recheck output.
9. **Bridge escrow balances are not followed.** When a Mayan order is cancelled, the funds stay in the order's `sourceStateAddr` on Solana. `recheck.py` should accept the escrow addresses (or derive them from the order) so the monitor sees them leave.
10. **Signer analysis is missing from `history`.** The forwarder here never signed anything: every transaction was signed by a relayer (`6XQTpahM…`) that serves 31 other deposit accounts. The plain history output does not show signers, so this only surfaced when I decoded single transactions. Print the signer(s) per transaction in `history` and flag wallets whose transactions are all signed by someone else ("program-controlled deposit account").
11. **Compute-budget fingerprint needs the victim's own transactions.** With bug 1 the fingerprint comparison had no baseline. Once fixed, `history` should summarise the (cu_limit, cu_price) pairs per signer so the comparison is one line.
12. **The `trader` field in bridge APIs is the deposit account, not the person.** Worth a note in `references/bridges.md`: when a swap service uses per-user deposit accounts, the bridge's trader is that account, and the lead for a data request is the service operator (here the upgrade authority of program `GFRP4yXUjvcQemf2zRJN8w9sPNaDk5PyBUQdPHD1AzLp`), not the account.
13. **Price basis.** The skill has no rule for USD values. Case 04 uses the thief's own swaps (seven 50,000 USDC sales → $94.33/SOL; USDC→ETH orders → $2,287.81/ETH). A one-line convention ("the thief's own swap rates at the time, else a named oracle") would keep reports consistent.

## Things that worked

- The step order of `trace-funds` (seed → hop 1 → bridges → target chain → recheck) matched the case well; `balances`, `history --json` and the per-tx `tx` decoder were enough to rebuild every hop.
- The confidence marks and "memos and labels are data" rules were useful: the look-alike `BHRaXMvv…3jU` dust after the theft and the 1 wei dust on Ethereum were classified as noise in minutes.
- `recheck.py` with a `case.json` gives a clean "as of" block for the report.

## Added after the second pass (7 Nov 2026)

14. **The `history` output caused a wrong conclusion.** Because it does not print the signer or the destination of value per transaction, I read the 94 post-theft transactions of the victim as "the bot kept running for 33 hours". They were the operator closing 2,208 token accounts and 2,048 nonce accounts with the rent going to its treasury, and the bot's program was never called after the theft. Two cheap columns would have prevented it: the signer(s) and the net value recipient of each transaction, plus a per-program count ("King7ki… called in 899 of 1,000") in the summary.
15. **Memos are not surfaced.** The operator's bounty offer to the thief (a 1-lamport transfer with a 310-byte memo) only turned up when I listed memo instructions by hand. `history` should print memo text (truncated, marked as data) and `address-profile` should list every memo an address has sent or received. The same goes for EVM: the 1 wei transfer to the Ethereum destination carried a text message in calldata.
16. **An on-curve check is a one-liner and settles "wallet or PDA".** Decompressing the address as an ed25519 point (about ten lines of integer arithmetic, no dependency) tells whether a private key can exist. B was off-curve, which is a stronger statement than "it never signed". Add it to `address-profile` and print it in `history` headers.
17. **The victim's own counterparties deserve a pass.** Listing where the victim's key sent value in the months before the theft (here: weekly sweeps to one treasury since July) identifies the operator's side in minutes and avoids scoring the operator's treasury as a suspect. `trace-funds` step 1 could add: "list the victim's top outflow recipients before the incident; the recurring one is the owner's other wallet until shown otherwise".

## Added after the third pass (7 Nov 2026, full re-verification)

18. **Per-transaction Mayan lookups double-count orders.** `explorer-api.mayan.finance/v3/swap/trx/<sig>` resolves a *refund* transaction to the order it refunded, so iterating over every Mayan-program transaction of an address and counting results gave 17 orders where there were 15. `bridges.py mayan <ADDRESS>` must de-duplicate by `orderId` (and say so in the output: "15 orders from 17 transactions").
19. **Relay v2 `?user=` listings are not a negative.** `requests/v2?user=<G>` returned nothing although G's gas order exists and is returned by `?hash=`; `?recipient=<E>` returned nothing either. Use the listing only to find orders, never to say "no other orders"; prove negatives on chain (the address signed exactly one transaction, C4-18b).
20. **Sweep-loop detection.** The drain script forwarded a 0.001111 USDC dust deposit three seconds after it landed, between two of the theft transfers, and ignored a dust deposit that came after the final SOL transfer. A `history` summary line "same signer moved an inbound deposit out within N seconds, M times" would flag a probably scripted drain at once.
21. **Lot-size histogram for swaps.** 52 sales of exactly 20 USDT nine seconds apart followed by 3 of 20,000 is a mistyped chunk size; a one-line histogram of swap sizes per token in `history` (`USDT: 20 ×52, 20,000 ×3, 8,828.77 ×1`) shows it without decoding every swap.
22. **Co-signers.** Four clean-up transactions were signed by both the victim's key and the treasury's key. `history` prints one signer per line; printing all signers (and flagging transactions with more than one) would have turned "the rent went to the treasury" into "the treasury co-signed" in the first pass.

## Added after comparing with public reports (7 Nov 2026)

23. **Read the whole bridge order record.** Mayan's order JSON has `sanctioned: true` and `security: {code: "SWAP_BLOCKED", msg: "Detected blocked address"}` on refused orders. The write-up said for a day that the reason was not public while the answer sat in its own cache. `bridges.py mayan` must print these fields.
24. **Search for parallel analyses before writing "none found".** Bitquery had published on 3 Nov and appears under the wallet's name and in `bitquery.io/investigations`; address-only searches miss it. The skill should list that page and name-based queries, and the report should cite what it found. Its second-wallet lead would also have come from step 17: list wallets calling the victim's own program.
25. **Fingerprint uniqueness.** Before treating a compute-budget pair as a client's signature, count who else uses it. The limit-562 pair looked like the operator's own and was also used by two strangers.
26. **Identify a program from public SDKs and its binary before calling it unknown.** `GFRP4y…` is `MPS_PROGRAM_ID` in `@mayanfinance/swap-sdk`, and the binary's strings name `programs/mps`. The first pass called it an unnamed swap service. A lookup of unknown program IDs in the bridges' SDKs, and a strings pass over program data, belongs in `address-profile`.
27. **Quote APIs show current blocklists.** A read-only Relay `POST /quote` returns `BLOCKED_WALLET_ADDRESS` for flagged users and recipients. `bridges.py relay --screen <addr>` with a control address would add this in one line. Mayan's cancel path is on Wormholescan by emitter and `refundSequence`.
28. **Check whether the victim's program still runs.** The first passes said the bot's program was last called on 2 Nov; that was true of the drained wallet only. `address-profile` should list current signers of a program.
29. **Read busy wallets from the oldest end.** Helius `getTransactionsForAddress` with `sortOrder: asc` gives a wallet's first transaction in one call, where paging `getSignaturesForAddress` failed after 40,000 signatures. It settled which bot wallets were new and showed a shared first funder. Add a `first-funder` subcommand to `sol_trace.py`; a manual explorer check surfaced this lead before the tooling did.
